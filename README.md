# Commandex Business Assistant

> Мультиагентный backend для операционных команд: он превращает сообщения и документы в структурированные события, контролируемые решения и проверяемые рабочие процессы.

Это portfolio-версия более крупной закрытой реализации. Здесь нет учётных данных, клиентских записей, реальных адресов, личных переписок и production-токенов.

## Что демонстрирует проект

Commandex Business Assistant объединяет сообщения из MAX и Telegram, приводит их к единой модели событий, извлекает структурированные факты с помощью LLM, сохраняет историю и направляет исходящие действия через политики и ручную проверку.

Основные возможности:

- событийный приём данных: аутентификация вебхуков, нормализация, дедупликация и асинхронная обработка;
- мультиагентный workflow для фактов, объектов, документов, отчётов, платежей и коммуникации;
- контролируемая автоматизация с согласованием, паузой диалога, защитой первого контакта и ключами идемпотентности;
- интеграции с PostgreSQL, Redis/ARQ, Google Drive, Google Sheets и LLM-провайдерами;
- авторизованная операционная панель для очередей проверки, объектов, людей, знаний, платежей и состояния системы;
- хранение секретов через окружение, минимальные права облачных интеграций и отсутствие production-данных в репозитории.

## Архитектура

Поток обработки выглядит так:

`MAX / Telegram` → `адаптеры вебхуков` → `нормализованные события` → `PostgreSQL и ARQ` → `агентный конвейер` → `состояние домена` → `проверка и policy` → `очередь исходящих сообщений`.

Операционная панель и адаптеры Google Drive / Sheets читают доменное состояние отдельно. LLM предлагает извлечение, классификацию и черновики, но не может напрямую изменить произвольное состояние или отправить сообщение внешнему человеку.

## Демо для портфолио

В каталоге `demo/` находится синтетический payload и сценарий показа без подключения реальных аккаунтов. Используются вымышленные имена и объект «Северный парк / квартира 12». Материалы подходят для code review и собеседования.

## Быстрый запуск

Требуются Python 3.12+, Docker Compose, PostgreSQL 16 с pgvector и Redis 7. Скопируйте `.env.example` в `.env`, укажите нужные провайдеры и выполните:

    make install
    make test
    make lint
    docker compose up -d --build

В development-режиме внешние вебхуки по умолчанию не регистрируются. Production-учётные данные и настройки конкретного заказчика должны храниться вне репозитория.

## Результаты проверок

Portfolio-снимок проверен полным набором из **754 успешно пройденных тестов** и чистым Ruff. Тесты охватывают нормализацию событий, дедупликацию, маршрутизацию агентов, обработку документов, policy исходящих сообщений, веб-аутентификацию, платежную логику, интеграции и процессы ревью.

## Структура проекта

- `src/repairbot/domain` — доменные события, факты, платежи и базовые объекты;
- `src/repairbot/agents` — агентный конвейер и бизнес-workflow;
- `src/repairbot/channels` — адаптеры каналов и нормализация платформ;
- `src/repairbot/outbound` — согласование, policy, очередь и доставка;
- `src/repairbot/web` — операционная панель и шаблоны;
- `src/repairbot/integrations` — клиенты LLM, Drive, Sheets и внешних сервисов;
- `tests` — модульные и интеграционные тесты;
- `docs/PORTFOLIO.md` — подробный кейс для портфолио.

## Безопасность

Не добавляйте в Git `.env`, `secrets/`, OAuth-токены, тома базы данных, выгрузки клиентов и реальные webhook URL. Production-развёртывание требует отдельного хранилища секретов, резервного копирования, мониторинга, rate limits, CSRF-защиты административных форм и операционного runbook.

## Лицензия и использование

Репозиторий представляет инженерную работу в формате портфолио. Перед использованием в production проверьте лицензии зависимостей, threat model, требования к хранению данных и условия выбранных мессенджеров.
